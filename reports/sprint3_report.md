### นายภาวัต วงศ์มาลาสิทธิ์ — Planner

- ออกแบบ **ผังหน้าจอทั้ง 4 Frame** และเส้นทางการสลับระหว่างหน้า ก่อนเริ่มเขียนโค้ด
  เพื่อให้ Coder ทั้งสองคนแบ่งไฟล์กันทำได้โดยไม่ชนกัน
- เขียน **Definition of Done 13 ข้อ** ของ Sprint 3 ใน `PLAN.md`
- **ตัดสินใจว่าจะไม่เขียน GUI ทับตรรกะเดิม** — ชั้น `game_state` · `minigame` ·
  `fish_api` ที่ทำไว้ใน Sprint 2 ต้องถูกเรียกใช้ตามเดิมทั้งหมด สปรินต์นี้เพิ่มเฉพาะ
  ชั้นแสดงผลเท่านั้น
- ส่งต่อประสบการณ์จาก Sprint 2 ให้ทีม — คลาส `QTEMinigame` ถูกออกแบบให้
  **ฉีดนาฬิกาเข้ามาได้ตั้งแต่ต้น** การเปลี่ยนไปใช้ `root.after()` จึงไม่ต้องแก้ตรรกะเลย

### นายศุภชัย คนเพียร — Coder (โครงหน้าต่างและการสลับหน้าจอ)

- พัฒนา `src/gui/app.py` คลาส `FishingApp` สืบทอดจาก `tk.Tk`
  ทำหน้าที่ถือสถานะเกมและสลับ Frame ทั้ง 4 หน้า
- **เปลี่ยนตัวจับเวลาของมินิเกมมาใช้ `root.after()`** โดยส่งเข้าไปทาง
  พารามิเตอร์ `clock` ที่มีอยู่แล้ว ไม่ต้องแก้ `src/minigame.py` แม้แต่บรรทัดเดียว
- ผูกเหตุการณ์ปิดหน้าต่าง (`WM_DELETE_WINDOW`) ให้เรียก `SaveManager.save()`
  ก่อนออก ผู้เล่นจึงไม่เสียความคืบหน้า
- **เจอปัญหาชื่อชนกับ tkinter** — ตอนแรกตั้งชื่อ property ว่า `state`
  ซึ่งไปทับเมธอด `tk.Tk.state()` ที่มีอยู่แล้ว แก้โดยเปลี่ยนเป็น `game`
  (รายละเอียดในข้อ 5.2)

### นายยศพล ถิรพงศชาติ — Coder (ตารางคลังสินค้าและตัวกรอง)

- พัฒนา `src/gui/frames.py` โดยเฉพาะหน้า Inventory ที่ใช้ `ttk.Treeview`
  แสดงปลาในกระเป๋าเป็นตาราง
- ทำให้ **คลิกหัวคอลัมน์แล้วเรียงลำดับได้ทั้งขึ้นและลง** โดยเรียกใช้
  `GameState.sort_inventory()` เดิม ซึ่งใช้ `sorted()` จึงไม่ทำลายลำดับจริงในกระเป๋า
- ย้ายระบบ **ค้นหาและตัวกรอง** จากเมนู CLI ขึ้นมาเป็นช่องกรอกและ dropdown บนหน้าจอ
  โดยเรียกฟังก์ชันเดิมของ `GameState` ไม่เขียนตรรกะซ้ำ
- แสดงสถิติเชิงลึกจาก `GameState.summary()` — จำนวนปลา มูลค่ารวม น้ำหนักเฉลี่ย
  และตัวที่หนักที่สุด
- ยืนยันด้วยการทดสอบจริงว่าเรียงลำดับ ค้นหา และกรอง ทำงานถูกทั้งหมด
  โดยไม่ต้องเขียนตรรกะใหม่เลยสักบรรทัด เรียกของเดิมจาก `GameState` ล้วนๆ

### นายธนภัทร สมบูรณ์ — Debugger / QA

- เขียน `tests/test_gui_logic.py` โดยยึดกติกาสำคัญข้อเดียว —
  **เทสต์ต้องไม่สร้าง `tk.Tk()`** เพราะเครื่อง CI ไม่มีจอ ถ้าสร้างจะพังทันที
  วิธีคือทดสอบเฉพาะฟังก์ชันที่ตัดสินใจ เช่น "ปุ่มซื้อควรถูกปิดหรือไม่"
  แยกออกมาจากโค้ดที่วาดหน้าจอ
- ตรวจว่า **เทสต์เดิม 135 เคสยังผ่านครบ** หลังแปลงเป็น GUI
  ถ้ามีเคสไหนพัง แปลว่ามีตรรกะรั่วเข้าไปอยู่ในชั้นหน้าจอ
- ทดสอบกรณีขอบเขตของหน้าจอ — กดปุ่มหลังหมดเวลา · ขายปลาตอนกระเป๋าว่าง ·
  ซื้อของตอนเงินไม่พอ · เรียง `finish()` ทั้งที่ยังไม่เริ่มรอบ
- ทำให้ `test_gui_logic.py` มี **77 เคส** และเพิ่มอีก **36 เคส** ใน
  `test_game_state.py` สำหรับกฎการขาย การแก้ไขข้อมูล และ Custom Exception
  กับอีก 7 เคสใน `test_validators.py` สำหรับการตรวจชื่อปลา
  เทสต์เดิม 135 เคสยังผ่านครบ
- เพิ่ม **เทสต์ประสิทธิภาพ** — สร้างกระเป๋าปลา 1,000 ตัวแล้ววัดเวลาการเรียง
  การค้นหา และการสรุปสถิติ ตั้งเพดานไว้ที่ 50 มิลลิวินาทีต่อการดำเนินการ
  เทสต์จะ fail จริงถ้าใครเขียนอัลกอริทึมที่ช้าลงในอนาคต

```

src/gui/widgets.py         Presentation Layer — การ์ด · แถบเวลา · คีย์แคป · ไทล์ตัวเลข

src/gui/frames.py          Presentation Layer — Dashboard · Fishing · Shop · Inventory
tests/test_gui_logic.py    ชุดทดสอบตรรกะของหน้าจอ โดยไม่สร้างหน้าต่างจริง
src/cli.py                 คงไว้เป็นโหมดสำรอง (ไม่ถูกลบ)
```

**ชั้นที่ไม่ถูกแก้เพื่องานหน้าจอ** — `src/minigame.py` · `src/worms_api.py` ·
`src/openfisheries_api.py` · `src/fish_api.py` · `src/save_manager.py`

ข้อนี้คือเครื่องพิสูจน์ว่าการแยกชั้นใน Sprint 1-2 ได้ผลจริง เปลี่ยนหน้าจอทั้งระบบ
โดยไม่ต้องแตะตรรกะเลย

**ข้อยกเว้น** — สามไฟล์ถูกแก้ในสปรินต์นี้ แต่**ไม่ใช่เพราะงานหน้าจอ** เป็นการเพิ่มกฎของเกม
จึงต้องอยู่ในชั้นของตัวเองตามหลักการเดิม ไม่ใช่การที่หน้าจอไปบังคับให้ตรรกะเปลี่ยน

| ไฟล์ | สิ่งที่เพิ่ม | ทำไมต้องอยู่ชั้นนี้ |
|---|---|---|
| `src/game_state.py` | `sell_fish()` · `sell_species()` · `count_species()` · `rename_fish()` · `set_keep()` · `toggle_keep()` · `kept_fish()` · `require_fish()` และ Custom Exception 2 ตัว | เป็น**กฎของเกม** — ปลาที่เก็บไว้ห้ามขาย และการอ้างถึงปลาที่ไม่มีต้องเป็น error |
| `src/fish.py` | ฟิลด์ `keep` และการอ่าน-เขียนฟิลด์นี้ลง JSON | เป็น**คุณสมบัติของปลา** ไม่ใช่สถานะของหน้าจอ |
| `src/validators.py` | `validate_fish_name()` | เป็น**การตรวจอินพุต** ซึ่งชั้น CLI และ GUI ใช้ร่วมกันได้ |

ทั้งสามไฟล์ยัง **ไม่ import tkinter** และยังถูกเรียกใช้จากโหมด CLI ได้เหมือนเดิม (ดูข้อ 5.5)

### 5.1 เทสต์ GUI บนเครื่องที่ไม่มีจอ

### 5.2 ตั้งชื่อ property ทับเมธอดของ tkinter

**ปัญหา:** ตอนแรกตั้งชื่อ property ที่เก็บสถานะเกมว่า `state`
ซึ่งไปทับเมธอด `tk.Tk.state()` ที่ tkinter มีอยู่แล้วสำหรับย่อ/ขยายหน้าต่าง
ถ้าปล่อยไว้ โค้ดที่เรียก `app.state('zoomed')` จะพังโดยหาสาเหตุยาก

**การแก้ไข:** เปลี่ยนชื่อเป็น `game` แล้วเขียน docstring บอกเหตุผลไว้กันคนแก้กลับ

**บทเรียน:** เวลาสืบทอดคลาสจากไลบรารี ต้องเช็กก่อนว่าชื่อที่จะตั้งไปชนกับของเดิมไหม

### 5.3 เปลี่ยนตัวจับเวลาโดยไม่ต้องแก้ตรรกะ

**สิ่งที่คาดว่าจะยาก:** มินิเกมของ Sprint 2 ใช้ `time.monotonic` ส่วน GUI ต้องใช้
`root.after()` คิดว่าจะต้องรื้อ `minigame.py` ใหม่

**สิ่งที่เกิดขึ้นจริง:** ไม่ต้องแก้ `src/minigame.py` แม้แต่บรรทัดเดียว
เพราะ Sprint 2 ออกแบบให้ฉีดนาฬิกาเข้ามาทาง constructor ไว้แล้ว
แค่เขียนคลาส `TkClock` ที่เดินหน้าทีละ 0.1 วินาทีทุกครั้งที่ `after()` ยิง แล้วส่งเข้าไปแทน

```python
class TkClock:
    def __call__(self):
        return self.now
    def tick(self):
        self.now += self.interval
```

**ผลพลอยได้:** `TkClock` ใช้ในเทสต์ได้ด้วย เพราะเดินเวลาเองได้โดยไม่ต้องรอจริง

### 5.5 ขายปลาทีละตัวและยกชนิด

**ที่มา:** เดิมขายได้แบบเดียวคือขายทั้งกระเป๋ารวดเดียว ผู้เล่นจึงเก็บปลาตัวใหญ่ไว้ไม่ได้
ถ้าอยากได้เงินก้อนเล็กก็ต้องยอมขายทิ้งทั้งหมด

**วางตรรกะไว้ที่ไหน** — กฎการขายเป็นเรื่องของโดเมน จึงเพิ่มไว้ใน `GameState`
ไม่ใช่ใน `frames.py` แม้จะเขียนที่หน้าจอได้เร็วกว่าก็ตาม

| เมธอดใหม่ | หน้าที่ |
|---|---|
| `sell_fish(fish)` | ขายตัวเดียว คืนราคาที่ได้ |
| `sell_species(name)` | ขายทุกตัวที่ชื่อตรงกัน คืน (จำนวน, เงินรวม) |
| `count_species(name)` | นับว่ามีชนิดนั้นกี่ตัว ใช้ตั้งข้อความบนปุ่ม |

**จุดที่ต้องระวัง — ปลาชื่อซ้ำกัน**

กระเป๋ามีปลาชื่อเดียวกันหลายตัวได้ แต่ละตัวน้ำหนักและราคาต่างกัน
ถ้า `sell_fish()` ค้นด้วยชื่อ จะขายผิดตัวทันที จึงเทียบด้วย**ตัวตนของอ็อบเจกต์**แทน
และมีเทสต์ `test_identical_fish_are_told_apart` คุมไว้

**การจับคู่แถวกับปลา**

`InventoryPresenter.fish_at(index)` อ่านจาก `visible_fish()` ตัวเดียวกับที่
`visible_rows()` ใช้ ลำดับจึงตรงกันเสมอ **แม้ผู้เล่นจะเรียงลำดับหรือกรองใหม่**
มีเทสต์ `test_row_index_follows_the_sort_order` และ
`test_row_index_follows_the_filter` คุมไว้ เพราะถ้าหลุดจุดนี้จะขายผิดตัวโดยไม่มีใครรู้

**บนหน้าจอ** — คลิกแถวแล้วปุ่มจะเปิดใช้งาน ปุ่มขายยกชนิดบอกจำนวนให้เห็นก่อนกด
เช่น `ขายทั้งชนิดนี้ (3 ตัว)` ยังไม่เลือกแถวปุ่มจะถูกปิดไว้

| `random_species()` ไม่รอเครือข่ายเด็ดขาด | ยังโหลดไม่เสร็จก็หยิบจากข้อมูลสำรองในเครื่องทันที |
| แยกสถานะทีละแหล่งน้ำ | น้ำจืดโหลดเสร็จก่อนก็ใช้ข้อมูลจริงได้เลย ไม่ต้องรอครบสามแหล่ง |
| โหลดพังก็ทำเครื่องหมายว่าเสร็จ | ไม่ค้างสถานะ "กำลังโหลด" ตลอดไป |

**ผลหลังแก้ (วัดจริงพร้อมยิงเครือข่าย)**

```
เปิดหน้าต่าง             0.67 วินาที
จับปลารอบ 1              0.02 วินาที
จับปลารอบ 2              0.00 วินาที
จับปลารอบ 3              0.00 วินาที
โหลดเบื้องหลังเสร็จใน    34.69 วินาที  (ผู้เล่นเล่นได้ตลอดเวลานี้)
จับปลาหลังโหลดเสร็จ      0.02 วินาที
```

หน้าแรกบอกสถานะให้เห็นด้วยว่า `กำลังโหลด` · `ออนไลน์` หรือ `ออฟไลน์`

**บทเรียน:** ชั้น Integration ถูกออกแบบมาอย่างดีเรื่องความถูกต้องและระบบสำรอง
แต่ไม่มีใครคิดเรื่อง **เวลา** จนกระทั่งเอามาต่อกับ GUI ที่เป็นเธรดเดียว
บั๊กแบบนี้ unit test จับไม่ได้เพราะเทสต์ใช้ตัวปลอมที่ตอบกลับทันที

## 6. Retrospective — Wow! & Whoops!

**Wow! (ส่วนที่ทำได้ดี)**

- **เปลี่ยนหน้าจอทั้งระบบโดยไม่ต้องแก้ตรรกะเพื่องานหน้าจอ** — `minigame.py` · `fish_api.py` ·
  `worms_api.py` · `openfisheries_api.py` · `save_manager.py` ไม่ถูกแตะเลย
  ส่วน `game_state.py` · `fish.py` · `validators.py` ที่ถูกแก้ ถูกแก้เพราะเพิ่มกฎของเกมใหม่
  (ขาย 3 แบบ · แก้ไขข้อมูล · Custom Exception) ไม่ใช่เพราะหน้าจอบังคับ
  เป็นเครื่องพิสูจน์ว่าการแยกชั้นใน Sprint 1-2 ได้ผลจริง
- **การฉีดนาฬิกาที่ทำไว้ล่วงหน้าคุ้มมาก** — เปลี่ยนไปใช้ `root.after()` ได้ฟรี
  ทั้งที่ตอน Sprint 2 ทำไว้เพื่อเทสต์อย่างเดียว
- ระบบค้นหา กรอง เรียงลำดับ ย้ายขึ้นหน้าจอได้โดยเรียกเมธอดเดิมของ `GameState` ล้วนๆ
  ไม่มีตรรกะซ้ำแม้แต่บรรทัดเดียว
- เทสต์ 137 เคสของสปรินต์นี้รันเสร็จในเสี้ยววินาที เพราะไม่มีเคสไหนเปิดหน้าต่างจริง
- **รื้อหน้าตาใหม่ทั้งหมดโดยไม่ต้องแก้เทสต์เลยสักเคส** เพราะการตัดสินใจ
  อยู่ใน `presenter.py` ส่วน `frames.py` แค่แปลงผลลัพธ์เป็นวิดเจ็ต

**Whoops! (ปัญหาที่พบและแนวทางแก้ไข)**

- **เกือบตั้งชื่อ property ทับเมธอดของ tkinter** — จับได้ก่อนเพราะไล่อ่านเอกสาร `tk.Tk`
  แก้เป็น `game` แล้ว (ดูข้อ 5.2)
- **`frames.py` ไม่ถูกครอบด้วย unit test** — coverage ของไฟล์นี้เป็น 0%
  เป็นการแลกที่ตั้งใจ เพราะถ้าจะเทสต์ต้องเปิดหน้าต่างจริงซึ่ง CI ทำไม่ได้
  ชดเชยด้วย smoke test ที่รันด้วยมือแทน
- **ลืมคิดเรื่องเวลาในชั้น Integration** — โค้ดถูกต้องและมีระบบสำรองครบ
  แต่ช้าจนหน้าต่างค้าง 34 วินาที ผู้เล่นเป็นคนเจอ ไม่ใช่เทสต์ (ดูข้อ 5.6)
- **ตอนแรกคิดจะเขียนตรรกะบางส่วนไว้ใน `frames.py` เพราะเร็วกว่า** — ยั้งไว้ทัน
  ถ้าทำไปแล้วจะเทสต์ไม่ได้เลย
