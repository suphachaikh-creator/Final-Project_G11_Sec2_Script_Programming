## 3. การเชื่อมต่อ Public API สองตัว

สปรินต์นี้ใช้ **Public API สองตัวที่เติมเต็มกัน** ทั้งคู่เรียกฟรีและไม่ต้องใช้ API Key

| API | ให้ข้อมูลอะไร | ระดับความสำคัญ | ไฟล์ |
|---|---|---|---|
| **WoRMS** | แหล่งที่อยู่ (น้ำจืด · น้ำเค็ม · น้ำกร่อย) และอนุกรมวิธาน | ข้อมูลหลัก — ขาดไม่ได้ | `src/worms_api.py` |
| **Open Fisheries** | ชื่อสามัญภาษาอังกฤษ | ข้อมูลเสริม — ล้มเหลวได้ | `src/openfisheries_api.py` |

เหตุผลที่ต้องใช้สองตัวคือ WoRMS เป็น API เดียวที่บอกแหล่งน้ำได้ แต่คืนมาแค่ชื่อวิทยาศาสตร์
อย่าง `Salmo salar` ซึ่งผู้เล่นอ่านไม่รู้เรื่อง ส่วน Open Fisheries มีชื่อสามัญอย่าง
`Atlantic salmon` แต่ไม่บอกว่าอยู่น้ำไหน เมื่อรวมกันจึงได้ทั้งสถานที่ที่ถูกต้องและชื่อที่อ่านง่าย

### 3.1 WoRMS — ชนิดปลาและแหล่งน้ำ

| หัวข้อ | รายละเอียด |
|---|---|
| Endpoint ที่ใช้ | `GET /AphiaRecordsByVernacular/{ชื่อสามัญ}?like=true` |
| เอกสาร | https://www.marinespecies.org/rest/ |
| คำค้นที่ใช้ | `carp` · `catfish` · `perch` · `tilapia` · `goby` · `snapper` · `grouper` · `mackerel` · `herring` · `shark` |

**ทำไมต้องใช้ endpoint ที่ค้นจากชื่อสามัญ** — WoRMS มีสอง endpoint ที่ใช้ค้นได้
`AphiaRecordsByName` ค้นจาก**ชื่อวิทยาศาสตร์** ส่วน `AphiaRecordsByVernacular`
ค้นจาก**ชื่อสามัญ** ทีมทดสอบทั้งสองตัวก่อนตัดสินใจ แล้วพบว่าการค้นคำอย่าง `fish`
หรือ `shark` ด้วยตัวแรกจะไปตรงกับสกุลของสัตว์กลุ่มอื่นที่สะกดคล้ายกัน เช่น *Fisherana*
ซึ่งเป็นหนอนทะเล **ผลคือได้ปลากลับมา 0 จาก 115 รายการ** ส่วนตัวหลังค้นเจอปลาจริง
**650 ชนิด** จึงเลือกใช้ตัวหลังเป็นหลัก

**การกรอง 3 ชั้น** — WoRMS มีทั้งหอย ปู และหนอน จึงต้องกรองก่อนนำมาใช้

| ชั้น | เงื่อนไข |
|---|---|
| 1 | `class` ต้องอยู่ใน 14 ชั้นทางอนุกรมวิธานของปลา |
| 2 | `status` ต้องเป็น `accepted` (ตัดชื่อพ้องและชื่อที่เลิกใช้) |
| 3 | ฟิลด์ `isFreshwater` · `isMarine` · `isBrackish` ต้องตรงกับสถานที่ที่ผู้เล่นเลือก |

### 3.2 Open Fisheries — ชื่อสามัญภาษาอังกฤษ

| หัวข้อ | รายละเอียด |
|---|---|
| Endpoint ที่ใช้ | `GET https://www.openfisheries.org/api/landings/species.json` |
| เอกสาร | https://www.openfisheries.org/api/ |
| ผลที่ได้จริง | 11,562 รายการ สร้างเป็นตารางจับคู่ได้ **8,672 คู่** |

### 3.3 การรวมข้อมูลสองแหล่ง

`src/fish_api.py` ทำหน้าที่ประสาน โดยจับคู่ทั้งสองแหล่งด้วย **ชื่อวิทยาศาสตร์**
(เทียบแบบไม่สนตัวพิมพ์เล็กใหญ่) ถ้าจับคู่ได้จะแสดงชื่อสามัญ ถ้าไม่ได้จะแสดงชื่อวิทยาศาสตร์แทน

```
WoRMS  ──► ชนิดปลา + แหล่งน้ำ + วงศ์
                    │
                    ├── จับคู่ด้วย scientific_name
                    │
Open Fisheries ──► ชื่อสามัญภาษาอังกฤษ
                    │
                    ▼
          ชื่อที่แสดงในเกม = ชื่อสามัญ (ถ้ามี) หรือชื่อวิทยาศาสตร์
```

**ผลที่ดึงได้จริงจากทั้งสอง API**

| สถานที่ในเกม | ฟิลด์ของ WoRMS | จำนวนชนิด | มีชื่อสามัญ |
|---|---|---|---|
| ทะเลสาบน้ำจืด | `isFreshwater` | 111 | 51 |
| ทะเลลึก | `isMarine` | 316 | 217 |
| ปากแม่น้ำน้ำกร่อย | `isBrackish` | 126 | 88 |

รวมจับคู่ชื่อสามัญได้ **64%** ของชนิดที่ดึงมา ส่วนในไฟล์ข้อมูลสำรองที่คัดไว้ล่วงหน้า
ทีมเรียงให้ชนิดที่มีชื่อสามัญขึ้นก่อนตอนตัดจำนวน จึงได้ชื่อสามัญ **ครบ 100%**

**แคชและระบบสำรอง** — ดึงจาก WoRMS **ครั้งเดียว** แล้วแยกแหล่งน้ำเอง ไม่ยิงซ้ำสามรอบ
และแคชผลไว้ต่อหนึ่งแหล่งน้ำ ถ้าเชื่อมต่อไม่ได้ `FishAPI` จะอ่าน `data/fish_species.json`
(แหล่งน้ำละ 30 ชนิด) แทน พร้อมตั้งธง `using_fallback` ให้หน้าจอแจ้งผู้เล่น
เกมจึงเล่นได้แม้ไม่มีอินเทอร์เน็ต

**ถ้า Open Fisheries ล่ม** เกมยังเล่นได้ตามปกติ เพียงแต่แสดงชื่อวิทยาศาสตร์แทนชื่อสามัญ
เพราะทีมออกแบบให้ `OpenFisheriesAPI` คืน dict ว่างเมื่อผิดพลาด ไม่โยน exception ออกมา

## 5. ปัญหาทางเทคนิคที่พบและวิธีแก้

### 5.1 มินิเกมที่จับเวลา ทดสอบอัตโนมัติไม่ได้

**ปัญหา:** โค้ดเดิมเรียก `time.time()` ตรงๆ ในลูปมินิเกม ถ้าจะเขียนเทสต์เรื่องหมดเวลา
ต้องให้เทสต์ `sleep()` รอจริงหลายวินาที ซึ่งทำให้ CI ช้าและผลลัพธ์ไม่แน่นอน

**การแก้ไข:** ทำให้ `QTEMinigame` รับ `clock` เข้ามาทาง constructor ตอนเล่นจริงใช้
`time.monotonic` ตอนทดสอบใส่นาฬิกาจำลองที่สั่งให้เดินหน้าได้ทันที
เทสต์เรื่องหมดเวลาทั้ง 4 เคสจึงรันเสร็จใน 0.16 วินาที

```python
class FakeClock:
    def __init__(self):
        self.now = 0.0

    def __call__(self):
        return self.now

    def advance(self, seconds):
        self.now += seconds
```

### 5.2 `FishAPI` เดิมเรียก API ไม่สำเร็จทุกครั้ง

**ปัญหา:** โค้ดเดิมตั้ง `url = ""` แล้วเรียก `requests.get(url)` ซึ่งล้มเหลวเสมอ
แล้วตกไปใช้ข้อมูลสำรองทุกครั้งโดยที่ไม่มีใครรู้ เพราะ `except Exception: pass` กลืน error ไว้

**การแก้ไข:** ชี้ไปที่ WoRMS API แยกการดัก error เป็นชนิดที่เจาะจง
(`ConnectionError` · `Timeout` · `HTTPError` · `JSONDecodeError`) และเก็บข้อความไว้ใน
`last_error` พร้อมธง `using_fallback` เพื่อให้หน้าจอแจ้งผู้เล่นได้ว่ากำลังใช้ข้อมูลสำรองอยู่

### 5.3 เรียงลำดับแล้วทำลายลำดับเดิมในกระเป๋า

**ปัญหา:** ถ้าใช้ `self.inventory.sort()` การเรียงเพื่อดูผลจะเปลี่ยนลำดับจริงในกระเป๋าถาวร
ซึ่งไปกระทบไฟล์เซฟตอนบันทึกครั้งถัดไป

**การแก้ไข:** ใช้ `sorted()` คืน list ใหม่แทน และเขียนเทสต์
`test_sort_does_not_mutate_inventory` คุมไว้ไม่ให้ใครเผลอเปลี่ยนกลับ

### 5.4 การเปรียบเทียบทางเลือกการจัดเก็บข้อมูล

| ทางเลือก | ข้อดี | เหตุผลที่เลือก/ไม่เลือก |
|---|---|---|
| **ไฟล์ JSON** | ไลบรารีมาตรฐาน อ่านด้วยตาเปล่าได้ แปลง `list` ของ `dict` ได้ตรงๆ | **เลือกใช้** — ข้อมูลเป็นสถานะผู้เล่นคนเดียว ไม่มีความสัมพันธ์ระหว่างตาราง |
| SQLite | รองรับข้อมูลใหญ่และ query ซับซ้อน | ไม่เลือก — เกินความจำเป็น ต้องเขียน schema และ query เพิ่มโดยไม่ได้ประโยชน์ |
| ไฟล์ข้อความธรรมดา | ง่ายที่สุด | ไม่เลือก — ต้องเขียน parser เอง และกระเป๋าปลาเป็นโครงสร้างซ้อนกัน |
